Trees in Space · TreeBot

The bot and web portal for Trees in Space, a Halo Infinite player community on Xbox. It automates what used to be tracked by hand in a spreadsheet: it detects group records from real match data, computes per-player and per-role stats, and publishes them on a public website and in the group's GroupMe chat.

Service architecture

  • Web bot (Flask on Render): receives GroupMe messages through a webhook, answers commands (records, personal stats, menu, a random snakemagic.com video), and serves the public records and roles site plus JSON endpoints.
  • Data layer (sheets.py): a single Google Sheets access module with a 5‑minute in-memory cache, shared by the bot and the scripts.
  • GitHub Actions workers: scripts that query the Halo API (records updater, per-player stats, nightly “GGs” recap, member onboarding) and write to the sheet or to GroupMe.
  • Google Sheets: works as the database: records, members, roles, stats, and a cache of Xbox IDs (XUIDs).

Data flow

  1. Source: Halo Infinite matches automated A daily workflow authenticates with Xbox Live and uses SPNKr to pull each member's recent matchmaking games.
  2. Processing automated It keeps wins in Big Team Battle, Squad Battle and Heavies with at least 5 group members on the same team (a community rule). Each result is compared with the current record for that map and mode (fastest time, or largest Slayer margin). Lifetime service-record stats are computed per player in the same run.
  3. Storage automated New records are written to Google Sheets and the previous one moves to “Good Times”. Stats go to their own sheet, and XUIDs are cached so lookups aren't repeated.
  4. Manual input manual Members are added through a manual workflow (gamertag as input), and each player's roles (Roamer, Anchor, Objective, Driver) are set with checkboxes in the sheet.
  5. Publishing automated, on request The bot reads the sheet (cached) and shows it on the public site (records, plus a roles page with sortable tables), through JSON endpoints, and as replies to GroupMe commands.
  6. Nightly recap on demand When someone types ggs in the chat, the bot triggers a workflow that summarizes the last few hours of games (W‑L score, match list and per-game leaders) and posts it to GroupMe in about a minute.

Challenges and technical decisions

  • Two Python runtimes

    The Render service runs an older Python than SPNKr requires (3.11+). Instead of a risky full migration, the heavy logic moved to GitHub Actions with its own dependency file, and the bot only triggers it through the GitHub API. The result is a lightweight web bot plus serverless workers.

  • Halo API rate limits (HTTP 429)

    Gamertag lookups were easily throttled. The fix added retry-with-backoff for 429 and 5xx responses, plus a shared XUID cache sheet so each player is looked up only once.

  • Data integrity

    The “record counts only with 5+ members” rule is enforced in code and is configurable. Heavies is classified by map and variant, and map names are normalized. A locale bug was also fixed: the sheet uses decimal commas, so 10,577 was being read as 10577; values are now read unformatted.

  • Secrets management

    Credentials were removed from the repository (explicit .gitignore), the service-account key was rotated, and everything is injected from GitHub Secrets and Render environment variables.

  • Hands-off operations

    Every workflow has a dry run mode and timeouts, and the stats step runs even if the records step fails. Daily upkeep needs no one, and changes can be tested without touching real data.

What it demonstrates

  • Automation and orchestration: scheduled and on-demand GitHub Actions pipelines, including runs triggered from an external app via workflow_dispatch.
  • API integration: four external services with different auth schemes (Microsoft/Xbox OAuth, Google service account, bot token, GitHub token).
  • Small-system design: separation of web service, data layer and workers; caching; rate-limit handling; idempotency and dry runs.
  • Pipeline-as-code and configuration management: versioned workflows, per-environment variables and centralized secrets.
  • Legacy refactoring: the bot started in 2022 and was reorganized into modules in 2026 (sheets.py, roles.py), with pinned dependencies and new features.
  • AI-assisted development: the 2026 modernization was designed and built in pair with Claude (Anthropic) as a coding agent, covering diagnosis, refactoring, new features and production debugging.
  • Real users: used daily by a community of about 30 players.

Goals

  • Stability: no command gets lost even when the free server is asleep, and failures are caught before the group notices.
  • History: store every match once in a database instead of querying the Halo API again on every command.
  • Presentation: nightly awards in the chat and a page per player with trends, best duos and strongest maps.
  • Advice, not just data: a coach! command that turns each player's stats into three concrete recommendations.

Target architecture

Phased plan

  1. Assessment planned Map of the current data flow and a list of weak points ranked by risk.
  2. Stability planned A single runtime (Python 3.11), immediate webhook response with background processing, health endpoint, retries with backoff, alerts and tests in CI.
  3. Database planned PostgreSQL schema with versioned migrations, idempotent match ingestion and a one-time migration from Google Sheets.
  4. Awards and player page planned Nightly MVP, most improved and best duo; a page with a 30-day trend, player synergy and strong and weak maps.
  5. AI coach planned coach! command with daily cache, cooldown and a non-AI fallback if the API is down.

Design decisions

  • Sheets for people, Postgres for machines

    The sheet stays as the control panel for what the group edits by hand. What the scripts generate (matches, dated stats, XUID cache) moves to tables, with history and fast queries.

  • The AI interprets, it does not calculate

    Python computes the comparisons (against the player's own average, the group's and by mode) and the model only turns them into advice. It cannot invent stats, and every recommendation is tied to a verifiable number.

  • Near-zero cost

    A free database plan that scales to zero, a small AI model with a per-player daily cache (fractions of a cent per request) and free monitoring services.

  • Negatives stay private

    Only shout-outs are posted in the group chat; areas to improve appear only when each player asks for their own stats.

What it will demonstrate

  • Reliability on free infrastructure: designing for servers that sleep, plus monitoring and alerts.
  • Data modeling: relational schema, versioned migrations and idempotent ingestion.
  • Applied AI with cost control: a language model integrated into a real product, with deterministically computed data.
  • Phased delivery: one branch and one pull request per phase, with automated tests.
