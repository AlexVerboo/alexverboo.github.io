Trees in Space · TreeBot

Bot y portal web de Trees in Space, una comunidad de jugadores de Halo Infinite en Xbox. Automatiza lo que antes se llevaba a mano en una hoja de cálculo: detecta los récords del grupo a partir de las partidas reales, calcula estadísticas por jugador y por rol, y las publica en una web pública y en el chat de GroupMe del grupo.

  • Python
  • Flask
  • GitHub Actions
  • Google Sheets
  • API de Halo Infinite
  • Xbox Live / Entra ID

Arquitectura del servicio

  • Bot web (Flask en Render): recibe los mensajes de GroupMe por webhook, responde comandos (récords, estadísticas personales, menú) y sirve la web pública de récords y roles, además de endpoints JSON.
  • Capa de datos (sheets.py): acceso único a Google Sheets con caché en memoria de 5 minutos; lo comparten el bot y los scripts.
  • Workers en GitHub Actions: scripts que consultan la API de Halo (actualizador de récords, estadísticas por jugador, resumen nocturno “GGs”, alta de miembros) y escriben en la hoja o en GroupMe.
  • Google Sheets: funciona como base de datos: récords, miembros, roles, estadísticas y una caché de identificadores de Xbox (XUIDs).

Flujo de datos

  1. Fuente: partidas de Halo Infinite automático Un workflow diario se autentica en Xbox Live y, con SPNKr, revisa las últimas partidas de matchmaking de cada miembro.
  2. Procesamiento automático Se filtran las partidas ganadas en Big Team Battle, Squad Battle y Heavies con al menos 5 miembros del grupo en el mismo equipo (regla de la comunidad). Cada resultado se compara con el récord vigente de ese mapa y modo (menor tiempo o mayor margen en Slayer). En paralelo se calcula el historial de por vida de cada jugador.
  3. Almacenamiento automático Los récords nuevos se escriben en Google Sheets y el anterior pasa a la sección “Good Times”. Las estadísticas se guardan en una hoja propia y los XUIDs se guardan en caché para no repetir búsquedas.
  4. Datos manuales manual Los miembros se dan de alta con un workflow manual (gamertag de entrada) y los roles de cada jugador (Roamer, Anchor, Objective, Driver) se marcan con casillas en la hoja.
  5. Publicación automático, bajo demanda El bot lee la hoja (con caché) y la muestra en la web pública (récords y una página de roles con tablas ordenables), en endpoints JSON y como respuesta a los comandos de GroupMe.
  6. Resumen de la noche bajo demanda Cuando alguien escribe ggs en el chat, el bot dispara un workflow que resume las partidas de las últimas horas (marcador W‑L, lista de partidas y líderes por promedio) y lo publica en GroupMe en aproximadamente 1 minuto.

Todos usan ubuntu-latest, Python 3.11, dependencias fijadas y credenciales desde GitHub Secrets. El despliegue del bot no pasa por Actions: Render lo despliega automáticamente desde la rama master. No hay workflow de pruebas automatizadas.

Retos y decisiones técnicas

  • Dos runtimes de Python

    El servicio en Render corre una versión de Python anterior a la que pide SPNKr (3.11 o superior). En vez de migrar todo de golpe, la lógica pesada se movió a GitHub Actions con su propio archivo de dependencias, y el bot solo la dispara por la API de GitHub. Resultado: un bot web ligero y workers sin servidor.

  • Límites de la API de Halo (HTTP 429)

    La búsqueda de gamertags se saturaba con facilidad. Se agregaron reintentos con pausa para 429 y 5xx, y una hoja de caché de XUIDs que comparten todos los scripts, de modo que cada jugador se busca una sola vez.

  • Integridad de los datos

    La regla “récord válido solo con 5 o más miembros” quedó en código y es configurable. Heavies se clasifica por mapa y variante, y los nombres de mapas se normalizan. Además se corrigió un error de configuración regional: la hoja usa coma decimal y 10,577 se leía como 10577; ahora se leen valores sin formato.

  • Gestión de secretos

    Las credenciales salieron del repositorio (.gitignore explícito), se rotó la llave de la cuenta de servicio y todo se inyecta desde GitHub Secrets y variables de entorno de Render.

  • Operación sin intervención

    Cada workflow tiene modo dry run y timeouts, y el paso de estadísticas corre aunque falle el de récords. Así el mantenimiento diario no requiere a nadie y se puede probar sin tocar datos reales.

Lo que demuestra

  • Automatización y orquestación: pipelines programados y bajo demanda en GitHub Actions, incluido el disparo desde una app externa vía workflow_dispatch.
  • Integración de APIs: cuatro servicios externos con distintos esquemas de autenticación (OAuth con Microsoft/Xbox, cuenta de servicio de Google, token de bot y token de GitHub).
  • Diseño de sistemas pequeños: separación entre servicio web, capa de datos y workers; caché; manejo de rate limits; idempotencia y dry runs.
  • Pipeline-as-code y gestión de configuración: workflows versionados, variables por entorno y secretos centralizados.
  • Refactorización de código heredado: el bot nació en 2022 y en 2026 se reorganizó en módulos (sheets.py, roles.py), con dependencias fijadas y nuevas funciones.
  • Desarrollo asistido por IA: la modernización de 2026 se diseñó e implementó en pareja con Claude (Anthropic) como agente de programación: diagnóstico, refactor, nuevas funciones y depuración en producción.
  • Producto para usuarios reales: lo usa a diario una comunidad de unos 30 jugadores.
